# Representative Work Review

- Repository: `jintonic1010/miracle_company_private`
- Branch: `main`
- Trigger: `/대표업무점검`
- Allowed role: `admin` only
- Mode: read-only

## 목적

관리자가 대표님과 회의하거나 업무를 확인하기 전에, 대표님이 남긴 회사 기록을 기준으로 다음을 빠르게 점검한다.

- 아이디어/문제가 저장돼 있는가
- 아직 미반영 상태인가
- PENDING_INDEX와 실제 대표님 기록 폴더가 일치하는가
- 대표님이 업무공유한 흔적이 있는가
- 저장된 내용 중 CURRENT_WORK에 연결되지 않은 것이 있는가
- 저장 기록 안의 일정/후속 액션 중 확인이 필요한 것이 있는가
- 관련 프로젝트의 실제 상태를 확인해야 하는가

이 기능은 대표님의 대화를 감시하거나 저장되지 않은 생각을 추정하는 기능이 아니다. **GitHub에 실제로 남은 기록만 감사한다.**

## Exact Trigger Gate

현재 사용자 메시지에 정확한 `/대표업무점검` 문자열이 있을 때만 실행한다.

- 관리자 프로젝트에서만 실행한다.
- 대표님 프로젝트에서는 존재를 설명하거나 실행하지 않는다.
- 읽기 전용이며 파일을 자동 수정하지 않는다.
- 점검 결과만으로 아이디어/문제/업무를 자동 반영·확정하지 않는다.

## 읽기 범위

최신 `main`에서 아래를 읽는다.

### 항상 읽기
- `FILE_MAP.json`
- `roles/REPRESENTATIVE.md`
- `records/PENDING_INDEX.md`
- `working/CURRENT_WORK.md`
- `working/HISTORY.md`
- `records/ideas/representative/` 파일 목록
- `records/problems/representative/` 파일 목록

### 필요 시 읽기
- 대표님이 작성한 개별 idea/problem 기록
- 기록이 연결한 `materials/normalized/representative/**`
- 현재 판단에 직접 관련된 `llm-source/` 문서
- 저장 기록이 실제 개발 완료/진행을 주장하고 그 사실 확인이 회의 판단에 필요한 경우 `llm-source/PROJECT_REPOSITORIES.md`에서 저장소를 찾아 해당 최신 `main`

다른 작성자의 전체 기록은 이 점검을 위해 읽지 않는다.

## 점검 로직

### 1. 대표님 저장 기록 Inventory

대표님 폴더의 실제 파일을 기준으로 아이디어/문제를 집계한다.

README 같은 안내 파일은 제외한다.

각 기록에서 가능하면 다음 메타데이터를 본다.

- title
- created_at
- status
- author_role
- 관련 업무/자료
- 후속 액션/기한

### 2. PENDING_INDEX 정합성

대표님 폴더의 `status: saved` 또는 미반영 상태 기록과 `records/PENDING_INDEX.md`를 비교한다.

다음을 구분한다.

- `정상 색인`: 미반영 기록이 index에 존재
- `색인 누락`: 대표님 기록은 있는데 pending index에 없음
- `유령 색인`: index에는 있는데 실제 기록 파일이 없음
- `상태 불일치`: 기록 상태와 index 상태가 맞지 않음

자동으로 고치지 않는다. 회의/관리 확인사항으로 표시한다.

### 3. 업무공유 흔적

`working/HISTORY.md`에서 `author_role: representative`, `representative`, `대표님` 작성자 표시가 있는 최근 업무공유/갱신 흔적을 확인한다.

현재 HISTORY 형식이 작성자를 명시하지 않은 오래된 기록이라면 그 사실을 표시한다.

GitHub에 공유 흔적이 없다고 해서 대표님이 실제로 일을 하지 않았다고 결론 내리지 않는다.

### 4. 저장 기록 ↔ CURRENT_WORK 연결

대표님의 미반영 아이디어/문제 중 현재 진행 중인 업무와 직접 관련된 것이 있는지 확인한다.

- 관련성이 높지만 CURRENT_WORK에서 전혀 보이지 않으면 `업무공유 검토 필요`
- 이미 CURRENT_WORK에 같은 내용이 있으면 `진행업무에 연결됨`
- 공식 기준과 충돌 가능성이 있으면 `반영 전 관리자 판단 필요`

이 단계에서 저장 기록을 공식 기준으로 취급하지 않는다.

### 5. 일정/후속 액션 체크

대표님 저장 기록 안에 날짜가 명시된 후속 액션이 있으면 현재 날짜 기준으로 분류한다.

- 예정
- 오늘/임박
- 기한 경과 — 완료 여부 확인 필요
- 완료 여부 확인 불가

기록에 날짜가 없으면 임의로 기한을 만들지 않는다.

### 6. 실제 확인 필요사항

대표님 기록이 다음을 주장하면 필요할 때 실제 근거를 확인한다.

- 개발 완료
- API 연결 완료
- 계약/견적 완료
- 데이터 적재 완료
- 외부 프로젝트 진행률

관련 프로젝트 저장소가 등록돼 있으면 최신 `main`을 확인할 수 있다.

다만 외부 현실 세계의 완료 여부가 GitHub에 없으면 `확인 불가`로 둔다.

## 출력 형식

기본 출력은 회의 전에 빠르게 볼 수 있도록 짧게 한다.

```text
대표님 업무 점검

기록 현황
- 아이디어: 총 N / 미반영 N / 색인 누락 N
- 문제: 총 N / 미반영 N / 색인 누락 N
- 최근 업무공유 흔적: YYYY-MM-DD 또는 확인 불가

관리 필요
- ...

업무공유 확인
- ...

일정/후속 액션
- ...

회의에서 확인할 것
1. ...
2. ...

권한 상태
- 대표님: 저장/검토/공유/반영미리보기 가능
- 실제 반영·확정: 관리자만 가능
```

문제가 없으면 억지로 항목을 만들지 않는다.

## 판정 원칙

`/대표업무점검`은 사람 평가 점수나 인사평가가 아니다.

다음처럼 표현한다.

- `정상 기록됨`
- `확인 필요`
- `업무공유 검토 필요`
- `반영 판단 필요`
- `기한 경과 여부 확인 필요`
- `GitHub 기록만으로 확인 불가`

대표님의 성실성, 능력, 의도 같은 성격 판단은 하지 않는다.

## 권한 경계

이 점검 이후에도 실제 변경은 별도 관리자 트리거가 필요하다.

- 아이디어 공식 반영: `/아이디어반영`
- 문제 공식 반영: `/문제반영`
- 진행업무 공식 확정: `/업무확정`

점검 중 발견한 PENDING_INDEX 누락이나 기록 오류도 자동 수정하지 않는다. 관리자가 별도 수정/반영을 지시해야 한다.

## Final Rule

`/대표업무점검`은 **대표님이 GitHub에 남긴 업무 기록의 관리 상태를 회의 전에 확인하는 관리자 전용 read-only 감사 기능**이다.

저장되지 않은 대화나 회사 밖에서 한 행동은 알 수 없으며, 모르면 반드시 `확인 불가`라고 표시한다.

# PMS Revenue SEO OS·워크북 v2 사업모델 비판적 검토

- 사업 범위: Premium MultiShop 전용
- BELLOON: 본 검토에서 제외
- 기준일: 2026-08-15
- 검토 대상: `business-wiki/plans/pms-automation-platform-v1-2026-08-13.md`, `Premium_MultiShop_Revenue_SEO_Workbook_v2.xlsx`, 전환·공급·디지털 포지셔닝 계획, 의사결정 로그
- 숫자 원칙: 문서에 이미 존재하는 하드스톱·게이트 외의 매출, 비용, 전환율, 현금, LTV 숫자는 입력 부재로 **검증 불가**로 표시

## 1. 한 줄 결론

현재 설계는 **SEO→상품발굴→소싱→판매→CRM→재구매의 통제 루프**로는 강하지만, 사업 전체를 운영하는 **현금·재고·법무·고객서비스·손익 계층**이 워크북과 OS에 분산되어 있다. 따라서 지금은 자동화 확대가 아니라 **통합 손익·현금·재고 원장과 운영 책임체계를 먼저 고정한 뒤 제한 테스트**해야 한다.

판정: **신규 대량 사입·유료 광고 확대·대규모 CRM·자동주문은 보류. 기존 재고 회수와 데이터 기준선 구축은 실행.**

## 2. 검토 기준과 확인된 전제

### 확인된 사실

- OS는 `Trend → Keyword → Sourcing → Profit → Decision → Content → Search → Order → CRM → Repeat` 루프와 Human-in-the-loop을 정의한다.
- 하드스톱은 순마진 12% 미만, 회수기간 6개월 초과, 데이터 신뢰도 0.70 미만, 재고회전일 90일 초과, 법적·정품 안전성 4/5 미만 등으로 기록되어 있다.
- 워크북 v2는 원본 01~06 시트를 보존하고 `07_경영대시보드`, `08_SEO콘텐츠매출`, `09_키워드상품판정`, `10_CRM재구매`, `11_데이터사전`을 추가했다.
- 07~11 시트는 SEO·CRM·키워드 판정의 입력과 일부 기여이익을 다루지만, 공급처·재고·주문·반품·현금 원장 자체는 포함하지 않는다.
- 전환 계획은 Cafe24·네이버/스마트스토어·카카오의 역할 분리, 창고/쇼룸, 출고·반품·A/S SOP를 제시하지만 다수의 목표값·비용·담당자는 미확정이다.

### 검증 불가

- 현재 월 매출·월 순이익·순마진율
- SKU별 실제 landed cost, 환율·관세·부가세·DDP/DAP, 플랫폼 수수료
- 주문일→정산일→반품종료일 기준 현금회수기간
- 채널별 CAC, 기여이익, 재구매율, LTV
- 재고 원가·노후화·실재 수량·회전일
- 반품·취소·하자·수선 비용 및 외주 SLA
- 고객 DB의 활성·동의·중복 제거 후 유효 모수
- 4개 매장 손익, 고정비, 임대차 종료비용, 온라인 이전율

## 4. 가장 큰 구조적 문제

### 4.1 성장 루프가 운영 루프보다 앞선다

OS는 발견과 노출의 흐름은 선명하지만 `매입 승인 → 현금 배정 → 입고 검수 → 재고 잠금 → 주문/출고 → 정산 → 반품 → 재고 처분`의 통제 흐름이 보조 설명에 머문다. 이 사업에서는 SEO가 잘되어도 공급·현금·출고가 막히면 성장할수록 손실이 커진다.

### 4.2 하드스톱이 SKU 의사결정에만 강하고 회사 전체에는 약하다

순마진 12% 미만 등은 상품 발주·확대 기준으로 명시되어 있으나, 광고·CRM·쇼룸·통합 거점·외주 A/S의 비용이 회사 전체 현금과 고정비를 잠식할 때의 중단 규칙은 연결되지 않았다. **상품 게이트와 사업 포트폴리오 게이트를 분리**해야 한다.

### 4.3 “기여이익”의 정의가 일관되지 않다

워크북은 콘텐츠/CRM 행별 기여이익을 계산하지만 SEO 콘텐츠 비용, CRM 비용, 배송·반품비, 상품원가의 포함 범위가 공통 원장으로 고정되지 않았다. OS는 CM1/CM2/CM3 개념을 제시하지만 워크북에는 회사·주문·고객·SKU를 연결하는 집계 키가 없다.

### 4.4 자동화 아키텍처가 데이터보다 앞서 있다

Customer/Product/Inventory/Order Master, API, Rule Engine을 잘 정의했지만 실제 API 권한·필드 매핑·정합성·소유자·복구·운영 비용은 검증 전이다. 현재는 “플랫폼 구축”보다 **읽기 전용 데이터 수집과 수동 승인 큐**가 적합하다.

## 5. 최적화된 사업 운영 구조: 계층

```text
L0 의사결정 헌법
  사업 분리(PMS/BELLOON) · 하드스톱 · 대표 승인 · 법적 안전성 · 데이터 신뢰도

L1 생존 통제층
  현금 13주/30일 · 고정비 · 채널 정산 · 재고 투자 한도 · 최대손실 · 세금/계약

L2 거래 원장층
  Customer Master · Product Master · Inventory Master · Order/Payment/Settlement · RMA
  모든 숫자는 SKU·주문·고객·채널·기준일·출처를 가진다.

L3 상품·공급 운영층
  공급처 증빙 → landed cost → SKU 승인 → 입고/검수 → 재고 잠금 → 가격/채널 배정

L4 이익 엔진층
  CM1(주문 직접비) → CM2(광고·CRM·콘텐츠) → CM3(운영·고정비) → 현금 기여

L5 수요·채널층
  SEO/콘텐츠 · Google/Naver · Cafe24 · 카카오 · 매장/쇼룸 · KREAM
  채널별 역할·가격·재고·귀속·의존도·중단조건

L6 고객·서비스층
  상담 → 구매 → 출고 → 배송 → 반품 → A/S/수선/관리 → 재구매
  동의·SLA·책임한도·서비스 원가·재구매 환류

L7 자동화·AI층
  읽기 → 후보 생성 → 예외 보류 → 승인 실행 순서
  AI는 가격·재고·주문·환불·고객 병합·대규모 발송을 직접 변경하지 않는다.
```

**운영 원칙:** 아래 계층의 통과 없이는 위 계층을 확장하지 않는다. 즉, L2 원장 없는 L5 광고 확대, L3 공급증빙 없는 Content Agent 공개, L1 현금표 없는 신규 사입은 금지한다.

## 6. 실행 우선순위

### P0 — 생존과 측정 기반

1. **단일 손익 사전 확정**: CM1/CM2/CM3, 순매출, 환불·반품 귀속, 콘텐츠/CRM/광고 비용, 고정비 배부를 한 페이지로 승인.
2. **현금 롤포워드 구축**: 다음 30일을 즉시 만들고, 운영 안정 후 주 단위 13주로 확장. 정산일·환불일·사입일·임대차·인건비·세금·이전비를 실제 날짜로 입력. 값은 입력 전 검증 불가.
3. **SKU·재고 원장 구축**: SKU별 원가/증빙/수량/입고일/상태/채널예약/노후화/최저가/중단사유. 국내재고·공급처재고·보류재고를 분리.
4. **주문·정산·채널 귀속**: Cafe24·네이버·카카오·매장·KREAM의 주문 ID, 고객 ID, SKU, 쿠폰, 수수료, 정산일, 상담 기여를 연결.
5. **반품·A/S 비용 원장과 SOP**: 사유코드, 환불일, 회수비, 재판매 가능 여부, 공급처 책임, 수선비·처리기간·클레임을 기록.
6. **동의·고객 ID 기준선**: 유효 동의, 철회, 중복, 매칭 확실성, 보관·접근권한을 확인. 현재 고객 모수는 검증 불가.
7. **기술 SEO P0 수정 전 광고 확대 금지**: 대표 도메인·모바일·상품 URL·템플릿·canonical/sitemap을 관리자 권한으로 변경 후 외부 재검증.

### P1 — 제한적 수익 검증

8. 기존 재고 3~5 SKU 또는 승인된 소량 범위에서 14/30일 테스트. 신규 사입은 OS 하드스톱과 최대손실을 모두 통과할 때만 대표 승인.
9. SEO 콘텐츠는 주제 클러스터 1개와 검증 상품만 연결. 조회수가 아니라 상품 클릭→상담→주문→CM2→재구매를 기록.
10. CRM은 동의·중복·빈도·세그먼트 통과 캠페인만 수동 승인 발송. 발송 전 예상 CM2와 실제 CM2 비교.
11. 창고/쇼룸 운영은 출고 SLA, 재고 정확도, 오출고, 반품 처리시간, 서비스 원가를 검증할 때까지 확장하지 않는다.

### P2 — 확장과 자동화

12. API는 읽기 전용 동기화부터 시작하고 오류 큐·재처리·감사 로그를 검증.
13. 통과한 규칙에 한해 재고 상태 동기화·고객 후보·콘텐츠 초안 자동화. 가격·주문·환불·대량 CRM은 계속 승인.
14. 월별 상품 포트폴리오/채널 포트폴리오 리뷰: 성장률보다 현금기여, 장기재고, 재구매, 플랫폼 의존도 기준.

## 한 문장 정의

**n8n은 회사 전체 OS의 뼈대이고, ERP/재고·물류, 시장리서치, 마케팅, CS, 세무·법률은 그 뼈대 위에서 연결되는 부서 시스템이다.**

## 회사 전체 구조

```text
Miracle Company OS
n8n = 회사 전체 연결·자동화 뼈대
ERP/재고·물류 ↔ 시장리서치 ↔ 마케팅 ↔ CS ↔ 세무·법률
       ↑↓
카페24 / 네이버 스마트스토어 / Google 관련 상품·판매 채널 IN/OUT
해외 공급처 API IN
       ↓
상품·SKU·재고·주문·판매·고객·물류 운영 Core
```

카페24·네이버·Google·해외 공급처 데이터의 **업무상 목적지는 ERP**다. n8n은 ERP 앞의 별도 데이터 소유 시스템이 아니라 회사 전체 부서·API·AI·자동화를 연결하는 뼈대다.

## n8n의 역할

회사 전체 부서 및 시스템 연결, 외부 API 연결과 워크플로 실행, 이벤트 기반 자동화, AI 에이전트 및 내부 서비스 연결, 반복 업무 오케스트레이션, 실패·재시도·알림 흐름의 공통 기반.

## ERP / 재고·물류 부서

ERP는 회사 운영 데이터의 핵심 부서이자 운영 원장이다. 관리 대상 후보는 상품, SKU/옵션, 재고, 창고, 입고/출고, 주문, 판매, 고객, 구매이력, 배송, 취소/반품/교환, 공급처, 구매/매입, 원가 및 정산에 필요한 운영 데이터다.
ERP 오픈소스 후보는 `ERPNext`와 `InvenTree`이며 아직 최종 확정하지 않았다.

## 외부 판매·공급 채널

- 카페24 ↔ ERP: IN/OUT 연결 대상
- 네이버 스마트스토어 ↔ ERP: IN/OUT 연결 대상
- Google 관련 상품·판매 채널 ↔ ERP: 실제 API 역할별 IN/OUT 조사 후 연결
- 해외 공급처 API → ERP: 상품·SKU·가격·재고·공급 가능 상태 등 필요한 데이터 입력

## 부서 간 데이터 흐름

ERP ↔ 시장리서치: 실제 판매·재고·고객·상품 성과를 활용하고 경쟁상품·시장가격·트렌드·신규상품 후보·공급처 후보 등의 판단 데이터를 반환한다.

ERP ↔ 마케팅: 고객·구매이력·상품·재고·매출 데이터를 활용하고 캠페인·세그먼트·프로모션·유입·전환·광고성과 데이터를 반환한다.

ERP ↔ CS: 고객·주문·배송·반품 상태를 활용하고 문의·클레임·처리결과·고객 피드백을 반환한다.

ERP ↔ 세무·법률: 거래·매출·매입·증빙·계약 관련 운영 데이터를 활용하고 처리결과·리스크·신고·증빙·계약 상태를 반환한다.

## 데이터 원칙

ERP가 모든 문서와 리서치 원문을 저장하는 것은 아니다. ERP는 운영 원장이고 리서치·마케팅·법률 문서·AI 분석 결과는 목적에 맞는 별도 저장소를 사용할 수 있다. 핵심 엔티티는 내부 기준 ID와 외부 채널 ID를 연결한다.

## 근거 기반 업무·품의 계층

위 부서·자동화 구조 위에 LLM 대화 → 원본 보존 → 전처리 → 조사·근거 → 작업 → 품의 → 관리자 결재 → 실행 결과 확인을 연결한다.
대표님은 방향·아이디어·요청, 부사수는 전처리·조사·실무·상신, 관리자 Jin은 최종 결재·우선순위·공식화 역할이다. 회사 운영 정책과 일반 결과물 승인은 구분한다.
GitHub는 이 계층의 문서·업무·결재 기록을 보존하며 ERP 운영 데이터를 대체하지 않는다. Higgsfield 등 제작 도구는 교체 가능한 실행 수단이고, 연결·실행 여부는 별도 확인한다.
도구가 바뀌어도 원본 ID, 출처·버전·기준일, 변환 이력, 업무 ID, 결과물 버전, 결재 범위는 유지한다.

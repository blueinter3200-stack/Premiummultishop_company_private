# 업무계획안제출 — GOV-20260907-01

정식 명령은 /업무계획안제출이다. 주 작성자는 부사수, 관리자도 자기 업무 계획을 작성할 수 있다. 대표님은 업무요청을 사용한다. 옛 명령은 실행하지 않는다. 내부 SUB-ID와 버전/본문 경로는 보존해 이름 변경으로 기록을 이동시키지 않는다.

## 두 가지 진입
1. 관리자 업무채택/배정 후: 자기 W와 현재 ASG의 승인된 업무 요약·목적·범위·기대 산출물을 기준으로 작성한다.
2. 대표님이 부사수에게 직접 구두 요청: 요청자와 전달/기록자를 구분해 R을 보존하고 검토 후 계획안을 바로 제출한다. W/ASG/사전 업무채택이나 별도 업무요청을 필수로 요구하지 않는다. 필요한 R 원문과 계획안은 한 커밋에 연결한다.
둘 다 계획 제출 자체로 관리자 승인·본 작업 착수·W를 만들지 않는다. 관리자에게 올라간 다른 대표 요청을 부사수가 전수 조회하여 임의 계획/배정하지 않는다. 자기 기록/대리 기록 또는 현재 관리자 배정의 승인된 요약만 사용한다.

## 준비 검토·내용
최신 공통 규칙·관련 R/W/ASG·현재 계획/D·EVIDENCE_STANDARD·APPROVAL_GOVERNANCE를 확인한다. 유효 검토가 없으면 준비 검토를 먼저 하며 PASS인 실제 후보만 정식 submitted로 제출한다. 핵심 충돌/근거 부족은 draft 또는 조사 범위 계획으로 표시한다.
R/ASG 출처, 요청자·발안자·실제 작성자·예정 수행자, 목적·방법·대안·판단 이유, 산출물·완료 기준, 비용/일정(미정은 null), 위험/미확인, 요청 승인 범위를 담는다. 현재 확보 자료의 정리·기획과 본 조사·개발·제작·지출을 구분한다. 후자를 품의 준비라고 무승인 수행하지 않는다.
내부 근거는 실제 파일 ID/링크·버전·시트/행·범위·기준일·상품/SKU다. 외부 근거는 실제 열어 본 링크·시점·영상 구간·관찰이다. 쇼츠는 실제 상품 데이터와 벤치마크 참고 요소를 연결한다. 3~5개 사례는 관련성 있는 목표일 뿐 미시청 자료로 숫자를 채우지 않는다. Hook/장면/자막/CTA와 게시 카피는 실제 확인 범위만 사용한다. 미검증 핵심 사실을 최종 검증 완료나 게시 가능한 사실로 내보내지 않는다.

## 버전·저장
새 SUB-ID는 SUB-<R-ID>-NNN, 기존 SUB-W 형식도 그대로 읽는다. 본문은 assistant/40-handoff/to-jin/<SUB-ID>-rN.md, metadata는 records/submissions/<SUB-ID>-rN.json이다. 수정본은 새 revision/파일이며 원본을 덮어쓰지 않는다.
metadata에는 plan_type=execution_plan, primary_scope=plan_execution, request_ref/content_revision/content_hash, work_id(null 가능), assignment_ref(null 가능), submitted_by_actor_id, proposed_assignee_actor_id, artifact_path/sha256, current_requirements, review_snapshot, requested_scopes, submission_status를 둔다. 본문은 원문 정본, metadata는 연결 정보다.
본문만/저장하지 마는 미저장 대화 초안이다. 정식 제출은 준비 검토→R/SUB 연결→본문/metadata→필요 W의 proposed_plan_ref/status 및 관리자 결정대기를 같은 변경 집합으로 저장한다. W가 있는 경우 현재 배정과 일치해야 한다. 새 r2를 제출해도 r1의 승인 범위를 자동 철회하지 않으며 r2 범위를 실행하지 않는다.
기존 결재된 요청 내용이나 본문 hash가 달라지면 계획 결의/본 수행 전에 재검토한다. 같은 source의 재시도/기존 R 상세화로 W나 R을 중복 생성하지 않는다.

## 결의와 실무
관리자는 /업무계획안결의에 승인/수정요청/보류/반려와 실제 이유·대상 버전·범위를 명시한다. 본 실행은 plan_execution과 research/production 등 실제 활동 범위, 현재 배정을 함께 확인한다. 아직 결정 없는 구두 요청의 계획에 업무채택·담당·실행을 명확히 함께 승인하면 한 동작으로 연결할 수 있다. 이미 보류/반려된 요청의 해제는 업무결정으로 별도 명시한다.
계획 준비 지시를 아직 작성되지 않은 모든 계획의 사전 승인으로 해석하지 않는다. 게시·지출·회사 기준 변경은 별도 범위다. 작성자는 자기 결재를 만들지 않으며 관리자 승인 전달만으로 승인 상태를 바꾸지 않는다.
COMMON_IO로 모든 변경 파일을 재조회하고 SUB-ID/revision/본문 경로·실제 커밋을 보고한다. 저장·실제 알림 표시·사람 확인은 별개다.

# 품의서 작성 — GOV-20260906-03

정식 명령: `/품의서작성`. 구 `/품의상신`은 동일 권한의 호환 별칭. 작성자: 관리자 또는 부사수. 최종 결재자는 ACT-001이다.

## 의미

근거·기획·초안·결과물과 승인받을 범위를 정리해 관리자 승인대기 품의서를 작성·저장한다. 명령 안내에서 저장 동작을 밝힌다. “본문만/저장하지 마”가 있으면 대화 내 초안만 작성하며 미저장·미상신이다. 저장은 관리자에게 자동 알림을 보낸다는 뜻이 아니다.

## 준비·검토

최신 공통 규칙과 대상 work/request, `templates/HANDOFF.md`, EVIDENCE_STANDARD, APPROVAL_GOVERNANCE를 읽는다. 명확한 work ID가 없으면 현재 요청으로 관련 업무를 찾는다. 순수 아이디어를 품의서 명령 때문에 실행 업무로 위장하지 않는다. 없는 상품·실적·벤치마크·파일을 채우지 않는다.
유효한 검토가 없으면 이 작성 요청에 포함된 준비 검토를 수행한다. 근거 부족은 추가 조사 요청 품의나 draft로 표시하며 verified_final이라고 하지 않는다. 검토 HOLD·핵심 충돌을 숨겨 승인 가능 품의로 제출하지 않는다.

## 반드시 포함

요청 원문·R-ID/지시 위치, 발안자/요청자/조사자/작성자 actor, work ID/revision, 실제 읽은 내부 파일 ID·버전·시트/범위, 실제 본 외부 링크·영상 구간, 적용 기준·대안·판단 이유, 기획·스토리보드·결과물 버전, 확인/미확인·위험·차단 조건, 요청 승인 범위.
쇼츠는 실제 상품 데이터와 실제 확인한 벤치마크의 참고 요소를 연결한다. 사례 3~5개는 관련성이 있을 때의 목표이며 미시청 자료로 숫자를 채우지 않는다. Hook·장면·자막·CTA 분석은 직접 확인 범위로 제한한다.
최종 검증 보고나 게시 카피는 미검증 주장을 제외하고 제외 후 결론이 무너지면 출력/게시를 막는다. 품의의 조사 질문·대안과 확정 사실은 다르다.

## 저장·버전

품의 ID는 `SUB-<work_id>-NNN`, 각 내용 수정은 revision을 올린 새 파일로 둔다. 예: `assistant/40-handoff/to-jin/<submission_id>-r1.md`. 승인 대상을 고정할 수 있도록 work revision과 각 artifact ID/revision/hash를 연결한다.
근거·버전·요청 범위가 정리된 품의는 submitted/approval pending으로 두고 work.submission_refs 및 관리자 결정대기를 함께 갱신한다. 미완성 초안은 draft이고 승인 준비 완료라고 표시하지 않는다.
COMMON_IO로 저장·재조회하고 실제 파일 경로·품의 ID/버전을 보고한다. 작성자가 승인 상태나 승인 기록을 만들지 않는다. 본문·첨부 변경 시 이전 승인을 자동 재사용하지 않는다.

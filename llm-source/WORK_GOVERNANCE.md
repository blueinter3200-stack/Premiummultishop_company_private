# Work Governance — GOV-20260906-05

## 객체와 권한
사람 ACT, 원문 요청 R, 아이디어 I, 문제 P, 품의 SUB, 결정 D, 실제 업무 W, 관리자 요청 변경 RC를 구분한다. 반복 방법은 플레이북이다. 대표님은 방향·요청, 부사수는 정리·계획·승인 범위 실무, 관리자 Jin은 최종 업무 결정·우선순위·회사 기준 변경을 담당한다.

## 표준 흐름
대화/원문 보존 → 업무검토 → 업무요청(간이 제출) 또는 품의서작성(상세 제출) → 관리자 업무결정/품의서결정 → 승인된 업무 → 업무업데이트 → 필요한 결과승인이다. 회사의 지속 기준 채택은 기준확정/아이디어반영/문제반영으로 분리한다.
요청 원문을 잃지 않기 위한 captured 저장은 사전 검토된 제출이나 착수 승인이 아니다. 실제 업무 생성은 관리자 work_start 승인 뒤에만 한다. W가 없는 사전 품의는 R에 연결한다. 동일 요청을 상세화한다고 새 R/W를 중복 생성하지 않는다.

## 검토
최신 공식 기준·관련 업무·PENDING_INDEX·REQUEST_INDEX·DECISION_INDEX와 직접 관련된 원문·정제자료를 읽는다. 실제 구현 질문만 해당 개발 저장소를 확인한다. 아이디어/문제/업무 후보/혼합/정책 변경을 분류하고 PASS/REVISION/HOLD와 권장 동작·이유를 남긴다. 단순 제안은 아이디어, 장애는 문제 기록으로 안내한다. PASS는 관리자 승인이나 자동 저장이 아니다.
같은 R/SUB는 현재 결정과 이력을 반드시 확인한다. 새 후보는 직접 동일/중복되는 건만 검색한다. 과거 반려·보류 사유, 현재 달라진 점, 해소 근거와 현재 제한을 구분한다. 관련 없는 과거 반려를 꺼내거나 작성자를 평가하지 않는다. 읽기 전용 검토는 원장·요청·알림 영수증까지 모두 비저장이다.

## 상태 원장
work/items가 수행 상태 원본이다. CURRENT_WORK와 assistant/30-working은 파생 화면이다. 요청과 품의의 결정 상태함은 개별 D와 현재 내용 버전에서 계산하는 조회판이며 원문을 상태별 폴더로 이동하지 않는다. pending·held·revision_required·approved·rejected를 분리한다.
업무업데이트는 관리자 또는 배정 부사수가 승인 범위의 기존 W를 갱신한다. 신규 업무 생성·승인·허용 범위 확대를 겸하지 않는다. 담당·기한 미정은 null이며 실제 수행자와 기록자를 구분한다. 완료에는 정해진 산출물·검증·필요 승인이 충족되어야 한다.
문제 저장만으로 업무 blocked나 문제 resolved를 만들지 않는다. 확인된 실제 영향이 있으면 별도 W 갱신으로 연결한다. 해결 방향 채택과 실제 해결은 다르다.

## 품의와 결정
품의에는 요청 원문, 실제 내부·외부 근거, 적용 기준·판단 이유, 기획·스토리보드·결과물 버전, 미확인, 요청 승인 범위가 있어야 한다. 상세 조사 자체가 미승인이라면 조사 범위를 요청하는 품의를 작성한다.
최종 결정은 ACT-001만 한다. 비승인 결정은 실제 이유를 기록하고 granted_scopes를 비운다. 기존 승인 범위 변경은 명시적인 철회/재결재 없이 뒤집지 않는다. 대표 발언·부사수의 승인 전달은 관리자 결정 증거가 아니다.

## 기록과 알림
새 I/P/R은 actor_id별 경로를 쓰고 과거 role 경로·ID·원문은 보존한다. 과거 결정도 변경하지 않는다. 현재 상태 변화는 새 D로 기록하고 새 사건 알림을 수신 actor별로 중복 없이 생성한다. 알림 읽음과 업무 완료는 무관하다. INBOX는 다음 업무 행동에서 선택 조회하는 파생 화면이다.
공식화·쓰기·실행은 COMMON_IO와 APPROVAL_GOVERNANCE를 따르고 성공한 경로·실패한 경로를 구분한다. 외부 게시·지출·운영 데이터 변경은 별도 승인 범위다. 관리자·대표 요청 충돌은 영향 범위만 보류하고 관리자가 조정한다.

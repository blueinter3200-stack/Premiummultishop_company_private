# Work Governance

- Repository: `https://github.com/jintonic1010/miracle_company_private`
- Branch: `main`
- Authority: official work-sharing governance
- Updated: 2026-08-21

## 목적

회사에서 진행·협의 중인 업무는 자유롭게 대화하되, `working/CURRENT_WORK.md`에 공유하기 전 **현재 확정된 회사 기준과 관련 미반영 아이디어·문제까지 함께 확인해 한 번 검토**한다.

진행업무와 공식 요구사항을 섞지 않기 위해 다음 흐름을 구분한다.

```text
자유로운 업무 대화
      ↓
아이디어/문제 저장 가능
      ↓
필요 시 /반영미리보기   ← 반영 시 예상 변화만 확인, read-only
      ↓
/업무검토
      ↓
공식 기준 + 현재 업무 + 관련 미반영 아이디어/문제 검토
      ↓
공유 가능 여부 판단
      ↓ PASS일 때만
/업무공유
      ↓
working/CURRENT_WORK.md 최신화
      ↓
관리자 판단
      ↓
/아이디어반영 · /문제반영 · /업무확정
      ↓
llm-source/ 공식 기준으로 승격/변경
```

대표님은 저장·검토·공유·반영미리보기까지 가능하다.
실제 공식 반영과 업무확정은 관리자만 가능하다.

## /반영미리보기

`/반영미리보기`는 대표님과 관리자가 사용할 수 있는 읽기 전용 영향 분석 기능이다.

목적은 저장된 아이디어·문제를 실제 반영하기 전에 다음을 보는 것이다.

- 현재 확정 기준
- 반영 시 예상 변경
- 영향 범위
- 기존 기준과의 충돌
- 아직 확인되지 않은 사실
- 예상 변경 파일

이 기능은 어떤 GitHub 파일도 수정하지 않는다.

미리보기에서 `반영 가능`해 보여도 실제 반영·확정 상태가 되지 않는다. 세부 규칙은 `llm-source/REFLECTION_PREVIEW.md`를 따른다.

## 관리자 /대표업무점검

`/대표업무점검`은 관리자 전용 read-only 관리 기능이다.

관리자는 회의 전에 대표님이 GitHub에 남긴 기록을 기준으로 다음을 확인할 수 있다.

- 대표님 아이디어/문제 저장 현황
- 미반영 상태
- 대표님 실제 기록 폴더와 `records/PENDING_INDEX.md` 정합성
- `working/HISTORY.md`의 대표님 업무공유 흔적
- 저장 기록과 `working/CURRENT_WORK.md` 연결 여부
- 기록 안에 명시된 일정/후속 액션 중 확인 필요사항
- 실제 프로젝트 상태 확인이 필요한 주장

이 점검은 인사평가가 아니며 대표님의 성실성·의도·능력을 추정하지 않는다.
GitHub에 저장되지 않은 대화나 회사 밖의 행동은 확인할 수 없으므로 `확인 불가`로 둔다.
점검 결과만으로 파일을 수정하거나 공식 반영하지 않는다.

세부 규칙은 `admin/REPRESENTATIVE_REVIEW.md`를 따른다.

## /업무검토의 기준

업무검토는 GitHub에 쓰지 않는 읽기 전용 단계다.

검토 시 최신 `main`에서 다음을 확인한다.

1. `FILE_MAP.json`
2. `llm-source/COMPANY_OS.md`
3. `llm-source/PRODUCT_REQUIREMENTS.md`
4. `llm-source/PROJECT_REPOSITORIES.md`
5. `working/CURRENT_WORK.md`
6. `records/PENDING_INDEX.md`
7. 현재 논의와 직접 관련된 `llm-source/departments/` 문서만 선택적으로
8. `PENDING_INDEX.md`에서 현재 업무와 직접 관련된 것으로 선별된 아이디어·문제 기록만
9. 선별된 기록이 연결한 `materials/normalized/` 자료 중 판단에 필요한 것만

### 미반영 아이디어·문제 읽기 원칙

`/업무검토`는 저장된 아이디어·문제의 존재를 무시하지 않는다.

다만 `records/ideas/**`, `records/problems/**` 전체를 매번 훑지 않는다.

먼저 `records/PENDING_INDEX.md`의 제목·요약·키워드·경로를 보고 현재 업무와 관련된 항목만 선별한다. 그 다음 관련 기록만 읽는다.

예:

```text
현재 업무: 마케팅 담당자 채용 기준 논의
        ↓
PENDING_INDEX 확인
        ↓
"CRM·ERP 데이터를 활용할 수 있는 마케팅 인력" 아이디어 발견
        ↓
해당 아이디어 파일만 읽음
```

이미 관리자에 의해 공식 반영된 아이디어·문제는 과거 기록을 다시 기본 컨텍스트로 쓰지 않고 `llm-source/`에 반영된 현재 공식 결과를 우선한다.

### 프로젝트 저장소 확인

현재 업무가 특정 구현 프로젝트와 관련되면 `llm-source/PROJECT_REPOSITORIES.md`에서 저장소명을 확인한다.

- 단순 저장소 위치 확인: 레지스트리만 사용
- 실제 개발 진척, 코드 상태, 구현 여부, 최근 변경 확인: 해당 저장소의 최신 `main`을 직접 확인

프로젝트 저장소 전체를 모든 업무검토마다 자동으로 읽지는 않는다. 실제 구현 사실이 검토 판단에 필요한 경우에만 확인한다.

## 업무검토 체크

- 현재 공식 회사 방향과 충돌하는가
- 기존 확정 요구사항을 변경하려는 내용인가
- 기존 CURRENT_WORK와 중복·모순되는가
- 관련 미반영 아이디어에서 이미 제안된 내용이 있는가
- 관련 미반영 문제에서 경고·장애·리스크가 저장돼 있는가
- 확정사항과 협의사항이 섞였는가
- 이미 폐기·보류된 내용을 되살리는가
- 주체, 범위, 조건 또는 다음 단계가 너무 모호해 공유 후 오해할 위험이 있는가
- 실제 확인되지 않은 추정치를 확정 사실처럼 쓰는가
- 고객정보·운영 DB·인증정보 등 GitHub 금지 데이터가 포함되는가
- 첨부자료가 있다면 원본 보존과 LLM용 Markdown 정제가 가능한가
- 특정 프로젝트 구현 상태가 핵심 근거라면 실제 해당 저장소 최신 `main` 확인이 필요한가

모든 항목을 형식적으로 채우게 만들 필요는 없다. **현재 진행상황을 다른 LLM/사람이 오해 없이 이어받을 수 있는지**가 핵심이다.

## 업무검토 결과

검토 결과는 셋 중 하나다.

- `PASS / 공유 가능`: 현재 내용으로 업무공유 가능
- `REVISION / 수정 필요`: 충돌·모호함을 고친 뒤 다시 검토
- `HOLD / 보류`: 현재는 공유하면 안 됨

`PASS`는 회사 공식 요구사항 확정을 의미하지 않는다. 진행업무판에 공유할 수 있다는 뜻이다.

업무검토 답변은 필요한 경우 다음을 구분한다.

```text
업무검토: PASS / REVISION / HOLD

현재 확정 기준
- ...

현재 진행/협의
- ...

관련 미반영 아이디어
- ...

관련 미반영 문제
- ...

검토 의견
- ...
```

관련 미반영 아이디어/문제가 없으면 없다고 짧게 표시하거나 생략할 수 있다.

## /업무공유 게이트

`/업무공유`는 같은 대화에서 가장 최근 `/업무검토`가 `PASS / 공유 가능`일 때만 실행한다.

검토 후 핵심 내용이 실질적으로 바뀌었다면 기존 PASS를 재사용하지 않고 `/업무검토`를 다시 실행한다.

업무공유 시:

1. 기존 `working/CURRENT_WORK.md`를 읽는다.
2. 현재 대화에서 검토 통과한 내용을 반영한다.
3. 새 내용 추가뿐 아니라 기존 내용의 수정·삭제·보류·완료도 반영한다.
4. 파일 전체를 다시 정리해 **현재 시점의 단일 최신판**으로 만든다.
5. 주요 변경 요약만 `working/HISTORY.md`에 짧게 추가한다.
6. `working/HISTORY.md`의 새 기록에는 가능한 경우 작성자 역할을 `representative` 또는 `admin`으로 명시한다.
7. 첨부자료가 있으면 가능한 경우 원본과 normalized Markdown을 분리 저장한다.

업무공유는 관련 아이디어/문제를 자동으로 공식 반영하지 않는다. 검토에서 참고한 미반영 아이디어/문제는 그대로 미반영 상태를 유지한다.

## 업무 첨부자료

업무공유에 첨부파일이 있는 경우:

```text
materials/originals/<author-role>/work/YYYY-MM-DD/<original-file>
materials/normalized/<author-role>/work/YYYY-MM-DD/<original-file>.md
```

- 원본은 보존용이며 기본 LLM 읽기 금지
- normalized Markdown은 필요한 본문·표·수치·날짜·결정·요구사항을 보존한 LLM용 정제본
- CURRENT_WORK에는 필요한 경우 normalized 경로만 연결
- 원본에 없는 사실을 추가하지 않는다

## /업무확정

관리자 전용이다.

CURRENT_WORK에 이미 공유된 항목 중 관리자가 명시적으로 확정한 내용만:

- `llm-source/COMPANY_OS.md`
- `llm-source/PRODUCT_REQUIREMENTS.md`
- 직접 관련된 `llm-source/departments/` 문서

에 반영한다.

기존 공식 요구사항을 추가·교체·삭제하거나 의미 있게 바꾸면 `docs/requirement-changelog.md`도 갱신한다.

확정 후 `CURRENT_WORK.md`는 다시 전체 최신판으로 정리해서 이미 확정된 내용과 아직 남은 협의사항이 섞이지 않게 한다.

관련 미반영 아이디어·문제가 업무확정의 근거로 사용됐더라도 자동으로 `reflected` 처리하지 않는다. 해당 기록 자체를 공식 반영하려면 관리자 `/아이디어반영` 또는 `/문제반영`을 사용한다.

## 기존 확정사항 수정

기존 공식 기준을 바꾸고 싶을 때도 바로 공식 문서를 고치지 않는다.

```text
변경안 논의
 → /반영미리보기 (선택)
 → /업무검토
 → PASS
 → /업무공유
 → CURRENT_WORK에 "기존 확정 / 변경 협의안"으로 기록
 → 관리자 /업무확정
 → 공식 기준 교체 + changelog
 → CURRENT_WORK 재정리
```

따라서 LLM은 변경 확정 전에는 다음처럼 구분해 답한다.

- `현재 확정 기준`: 기존 공식 소스
- `현재 협의/진행 중`: CURRENT_WORK의 변경안

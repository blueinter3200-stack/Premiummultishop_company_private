# Approval Governance — GOV-20260906-05

최종 결재자는 ACT-001 / admin / Jin이다. 업무요청은 업무결정, 상세 품의는 품의서결정으로 승인/수정요청/보류/반려한다. 결과물 수락은 결과승인, 회사 정책 채택은 기준확정·아이디어반영·문제반영으로 구분한다. 구명령과 별칭은 실행하지 않는다.

## 범위
work_start=요청된 일의 생성·착수 허용, research=조사, production=제작, deliverable=결과물 수락, publication=특정 계정·일정·문구·버전 공개, expenditure=금액·통화·기간·사용처, policy_change=회사 기준 변경이다. 여러 범위를 명시하여 한 번에 결정할 수 있으나 애매한 승인으로 확대하지 않는다. 품의서 승인에 work_start가 명시된 경우만 업무 생성/연결을 겸하며 승인 클릭 횟수를 중복 요구하지 않는다.

## 결정 기록
D-ID는 실제 관리자 발언과 대상 R/SUB/결과물의 정확한 내용 버전·해시, requested/granted scopes, scope_key, 이전 결정, 결정 이유·이유 출처·조건, 재검토 조건, 시각, 역할 확인 수준을 가진다. 신규 결정은 append-only다. 과거 D의 내용을 새 결과로 덮어쓰지 않는다.
승인=approved, 수정요청=revision_required, 보류=held, 반려=rejected다. 비승인은 granted_scopes=[]이며 실제 이유를 필수로 받는다. 이유가 이미 있으면 다시 묻지 않지만 없으면 결정 저장 전에 이유만 확인하고 AI가 채우지 않는다. 보류의 재검토 날짜/조건이 없으면 null이지 자동 기한이 아니다.
대상·결정값·버전·범위가 여러 개면 임의로 결정하지 않는다. 이유 표시 변경만으로 새 알림을 만들지 않으며 의미 있는 새 판단만 새 사건이다.

## 상태 전환과 재결재
pending→각 결정, held→approved/revision_required/rejected/의미 있는 held 갱신이 가능하다. 새 D가 직전 유효 D를 연결한다. 수정본 r2는 r1의 결정을 유지한 채 새 검토·결정 대상이다. 반려 후 재추진에는 명시적 재개 이유/변경 근거 또는 연결된 새 요청이 필요하다.
승인 후 중단/반려/범위 축소는 명시적 승인 철회·변경 근거와 영향 범위를 기록한 새 D로 처리한다. 특정 게시 품의 반려가 기존 조사 승인 전체를 지우지는 않는다. 같은 URL도 내용이 달라지면 재결재한다.
다른 사람의 'Jin 승인'은 approval_claim이다. 실제 관리자 원문과 대상·버전을 대조하고, 공유 계정/프로젝트 역할 확인을 독립 서명·본인 인증이라고 과장하지 않는다.

## 알림과 저장
D·관련 상태 연결·결정 인덱스·상태함·수신자별 알림 이벤트·INBOX를 같은 커밋으로 저장한다. 작성자·요청자와 직접 영향을 받는 담당자만 수신하고 관리자 자기 결정은 자기 알림을 기본 생성하지 않는다. 동일 사건 재시도는 D/N/W를 중복 생성하지 않는다. 상태 변경은 원문 이동이 아니라 조회판 재계산이다.
저장 후 모든 변경 파일을 재조회한다. 일부 실패는 부분 저장이며 알림 생성과 실제 표시·사용자 확인은 다르다. 자동 외부 푸시나 다른 채팅방 메시지 전송을 가정하지 않는다. 실제 외부 실행은 승인과 별도 요청·결과 검증이 필요하다.

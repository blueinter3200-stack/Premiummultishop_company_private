# Approval Governance — GOV-20260907-01

최종 결정권자는 ACT-001 / admin / Jin이다. 업무요청은 /업무결정, 실행계획은 /업무계획안결의에 승인·수정요청·보류·반려를 명시한다. 결과 수락은 /결과승인, 공식 기준 채택은 /기준확정·/아이디어반영·/문제반영이다. 구명령/별칭을 실행하지 않는다.

## 범위
work_adoption=회사 업무로 채택/등록, planning=계획 준비, plan_execution=특정 계획 버전·담당·배정에 대한 실행 허가다. research=조사, production=제작, deliverable=결과물 수락, publication=특정 계정·문구·일정·버전 공개, expenditure=금액·통화·기간·사용처, policy_change=회사 기준 변경을 함께 구분한다.
기존 work_start 결정은 당시 의미로 읽되 새 부사수 계획을 사전 승인하는 것으로 확대하지 않는다. 새 업무요청의 채택은 통상 work_adoption/planning이며 본 실행은 계획 결의에서 정한다. 관리자 자신의 명시 직접 수행은 본인 범위만 예외로 기록한다.
담당 배정은 ASG 사건이다. 업무 승인과 배정을 함께 말하면 함께 저장할 수 있으나 미지정 담당을 부사수로 추정하지 않는다. 작업지시나 구두 대표 요청만으로 계획 실행을 허가하지 않는다.

## 결정과 연결
정확한 R/SUB/산출물 내용 버전/hash, scope_key, requested/granted scopes, 실제 관리자 원문·locator·이유/조건·시각·선행 D·검증 수준을 기록한다. 계획실행 결정은 execution_assignee_actor_id와 assignment_ref도 고정한다. body hash 또는 R 내용이 바뀌면 재검토한다.
아직 결정 없는 구두 요청 계획안에 관리자가 업무채택·담당·계획실행을 명확히 함께 승인하면 한 동작으로 연결한다. 이미 보류/반려된 업무요청을 계획 결의로 무음 해제하지 않는다. 관리자 업무결정으로 재개 조건을 먼저 기록한다. 이미 채택된 같은 W에는 별도 W를 만들지 않는다.
승인=approved, 수정요청=revision_required, 보류=held, 반려=rejected다. 비승인은 실제 이유가 필요하고 granted_scopes는 빈 목록이다. 없는 이유/기한은 AI가 채우지 않는다. 결과값 없는 결재는 승인으로 추정하지 않는다.

## 변경·실행·알림
보류→승인/반려와 의미 있는 조건 변경은 새 D로 선행 결정을 연결한다. 반려 후 재개는 실제 재개 근거 또는 관련된 새 요청으로 검토한다. 승인 철회/중단은 명시적 변경·영향 범위와 revokes_decision_ids를 남긴다. 특정 계획 r2 반려를 기존 r1 실행 승인 전체의 취소로 확대하지 않는다.
대표님 발언/부사수 전달은 approval_claim이지 관리자 결정 증거가 아니다. 프로젝트 역할 기반 확인을 독립 계정 인증·서명으로 과장하지 않는다.
D·관련 W·ASG·조회판·수신자별 N을 같은 변경 집합으로 저장한다. 초기 대표 요청 결정은 요청자에게, 부사수 배정은 승인된 작업지시 요약으로 부사수에게 연결한다. 같은 배정 내용을 D와 ASG로 중복 방송하지 않는다. 기존 배정 업무에 영향을 주는 후속 보류/승인은 담당자도 안내받아야 한다.
실제 전달은 다음 관련 업무 대화의 INBOX 확인이며 실시간 푸시가 아니다. 조회/생성/표시/사람 확인/실제 수행은 따로 검증한다. 저장 후 모든 변경 경로를 재조회하고 부분 실패를 전체 성공으로 보고하지 않는다.

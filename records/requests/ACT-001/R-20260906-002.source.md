# 작업 지시

대상 저장소:

`jintonic1010/miracle_company_private`

대상 브랜치:

`main`

현재 확인된 기준 릴리스:

`GOV-20260906-03`

확인된 기준 커밋:

`d708129d0419ca61d79517344091f0b89d096932`

단, 위 커밋을 현재 HEAD라고 가정하지 말고 작업 시작 시 반드시 원격 최신 `main`을 다시 확인한다. `main`이 더 진행되어 있으면 최신 상태를 기준으로 작업하고, 위 커밋으로 reset하거나 최신 변경을 덮어쓰지 않는다.

---

# 1. 작업 목적

현재 회사 OS에는 명확한 회사 요청을 `R-ID`로 보존하고, 요청 수정·취소 시 revision 및 supersedes 관계를 남기는 체계가 있다.

이번 작업에서는 여기에 **관리자 ACT-001 / Jin이 한 사용자 요청이 의미 있게 변경될 경우, 변경 내용과 변경 이유를 독립적인 변경이력으로 추적하는 구조**를 추가한다.

목표는 나중에 다른 LLM이나 사람이 다음 질문에 GitHub 기록만으로 답할 수 있게 만드는 것이다.

- 최초에 Jin이 무엇을 요청했는가?
- 이후 무엇이 변경됐는가?
- 변경 전과 변경 후가 무엇인가?
- 누가 변경했는가?
- 왜 변경했는가?
- 어떤 업무·결정·요구사항에 영향을 줬는가?
- 실제로 무엇까지 수행·검증됐는가?

기존 코딩 프로젝트의 meaningful-change traceability 철학과 동일하게:

**what changed / why changed / evidence / impact / verification**

을 관리자 회사 요청에도 적용한다.

---

# 2. 절대 보존해야 할 기존 구조

기존 `GOV-20260906-03` 구조를 재설계하거나 초기화하지 않는다.

특히 다음을 보존한다.

- 기존 `R-ID`
- 기존 request 원문
- 기존 request revision
- 기존 supersedes 관계
- 기존 `W-ID`
- 기존 `D-ID`
- 기존 아이디어/문제 기록
- 기존 approvals
- 기존 materials
- 기존 actor\_id
- 기존 대표님/관리자/부사수 역할 경계
- 기존 15개 명령의 의미와 권한
- 기존 read-only 명령의 비저장 원칙
- 기존 요청 자동보존 예외 규칙
- 기존 배포/검증 규칙

과거 기록 전체를 새 스키마로 일괄 재작성하지 않는다.

새 체계는 **backward-compatible extension**으로 만든다.

# 4. 새 핵심 개념

기존 ID 의미를 유지한다.

- `R-ID` = 사용자가 무엇을 요청했는가
- `RC-ID` = 그 요청이 이후 어떻게, 왜 변경됐는가
- `W-ID` = 그 요청을 바탕으로 어떤 실제 업무를 수행하는가
- `D-ID` = 어떤 범위와 버전을 승인/결정했는가

새 ID:

`RC-YYYYMMDD-NNN`

RC는 `Request Change`를 의미한다.

---

# 5. 적용 대상

우선 **관리자 ACT-001의 요청에만 필수 적용**한다.

즉:

`requester_actor_id == ACT-001`

인 기존 요청의 의미가 이후 관리자 지시에 의해 materially changed 되었을 때 RC 기록을 생성한다.

대표님 ACT-002와 부사수 ACT-003에 같은 무거운 변경추적 규칙을 강제하지 않는다.

기존 대표님/부사수 request revision 동작은 깨지 않는다.

---

# 6. RC가 필요한 경우

다음 중 하나가 실질적으로 바뀌면 RC를 남긴다.

- 업무 목적
- 업무 범위
- 필수 조건
- 결과물 요구사항
- 대상 시스템
- 대상 사용자/담당자
- 우선순위가 실제 업무 수행에 영향을 주는 경우
- 완료 기준
- 승인 조건
- 지속 지시
- 기존 요청의 취소
- 기존 요청의 일부 철회
- 기존 요청의 대체
- 기존 요청에 대한 의미 있는 추가 요구사항
- 기존 요구를 다른 방향으로 변경하는 관리자 지시

예:

최초:

`구매이력 기반으로 상품 추천`

후속:

`구매이력뿐 아니라 고객 취향 데이터도 같이 사용`

→ RC 필요.

---

# 7. RC를 만들지 않는 경우

다음은 의미가 바뀌지 않으면 RC를 만들지 않는다.

- 오탈자 수정
- 띄어쓰기
- 문장 표현 정리
- 의미 없는 포맷 변경
- 링크 표시 방식만 수정
- 동일 요청의 단순 재확인
- 같은 내용을 다시 말함
- 단순 질문
- 아이디어 탐색
- 읽기 전용 검토
- 저장하지 말라는 요청
- 기존 read-only 트리거 실행

의미 없는 변경으로 로그를 과도하게 쌓지 않는다.

---

# 8. RC 저장 구조

현재 저장소 패턴을 우선 확인하되, 별도 충돌이 없다면 다음 구조를 사용한다.

```text
records/request-changes/
└─ ACT-001/
   └─ <R-ID>/
      ├─ RC-YYYYMMDD-NNN.json
      └─ ...

```

반복 구조이므로 적절한 template도 만든다.

예:

```text
templates/REQUEST_CHANGE.json

```

검색성과 운영성이 실제로 좋아진다면 다음 인덱스도 추가한다.

```text
records/REQUEST_CHANGE_INDEX.md

```

단, 인덱스는 정본이 아니다.

정본은 개별 RC JSON이다.

기존 저장소에 더 적합한 인덱스 패턴이 이미 있다면 그 패턴을 따른다.

---

# 9. RC 필수 데이터

실제 저장소 스타일에 맞춰 JSON schema를 정리하되 최소한 다음 의미는 보존한다.

```json
{
  "schema_version": 1,
  "object_type": "request_change",

  "request_change_id": "RC-YYYYMMDD-NNN",
  "request_id": "R-YYYYMMDD-NNN",

  "changed_by_actor_id": "ACT-001",
  "changed_at": "YYYY-MM-DD",

  "change_type": "modify | add_scope | remove_scope | replace | cancel | condition_change | other",

  "change_summary": "...",

  "changed_fields": [
    {
      "field": "...",
      "before": "...",
      "after": "..."
    }
  ],

  "change_reason": "...",

  "reason_source": "explicit_user_statement | source_evidence | unknown",

  "source_type": "...",
  "source_locator": "...",
  "source_excerpt": "...",

  "affected_work_ids": [],
  "affected_decision_ids": [],
  "affected_idea_ids": [],
  "affected_problem_ids": [],

  "unknowns": []
}

```

정확한 필드명은 기존 repository schema 스타일에 맞춰 조정 가능하다.

하지만 다음 정보는 반드시 추적 가능해야 한다.

1. 어떤 R-ID가 바뀌었는가
2. 누가 바꿨는가
3. 언제 바뀌었는가
4. 변경 전
5. 변경 후
6. 무엇이 바뀌었는가
7. 왜 바뀌었는가
8. 변경 근거가 어디에 있는가
9. 어떤 W/D 등과 연결되는가

---

# 10. 변경 이유 처리 규칙

`change_reason`을 절대 임의로 만들어내지 않는다.

관리자가 이유를 직접 말한 경우:

- 실제 발언 근거를 보존
- 필요한 경우 normalized reason도 저장

대화나 회사 자료에서 이유가 명확하게 확인되는 경우:

- 근거 위치를 연결
- `reason_source`에서 명시적으로 구분

이유를 확인할 수 없는 경우:

- 거짓 이유를 만들지 않는다.
- `change_reason: null` 또는 현재 schema에 맞는 unknown 표시
- `unknowns`에 변경 이유 미확인이라고 남긴다.

“변경했다”는 사실과 “왜 변경했는지”를 추측해서 섞지 않는다.

---

# 11. 원요청 불변성

기존 최초 요청의 원문을 새 요구사항으로 덮어쓰지 않는다.

예:

R-001 최초 원문:

`구매이력 기반으로 추천해`

후속 관리자 요청:

`고객 취향도 같이 사용해`

이 경우 R-001의 최초 원문을 후속 문장으로 교체해서는 안 된다.

현재 유효 범위가 request 파일에서 revision 형태로 갱신될 수는 있지만:

- 최초 원문
- 각 변경 이벤트
- 변경 이유

가 모두 복원 가능해야 한다.

RC는 원요청을 덮어쓰는 파일이 아니라 **변화의 역사**다.

---

# 12. Request 파일과의 연결

기존 `REQUEST.json` 구조와 backward compatibility를 유지하면서 가능하면 다음과 같은 연결을 추가한다.

예:

```json
"request_change_refs": [
  "records/request-changes/ACT-001/R-.../RC-....json"
]

```

또는 현재 schema convention에 맞는 동일 의미의 필드.

새 template schema version을 올리는 것이 타당하면 올린다.

단:

- 기존 v1 파일을 전부 강제 마이그레이션하지 않는다.
- 기존 기록이 읽히지 않게 만들지 않는다.
- 기존 request\_status 의미를 바꾸지 않는다.

---

# 13. revision과 RC의 관계

기존 request `revision`을 제거하지 않는다.

정의는 다음처럼 정리한다.

`revision`
\= 현재 request 객체가 몇 번째 갱신 상태인지

`RC-ID`
\= 의미 있는 사용자 요구 변경 사건의 독립적인 감사/추적 기록

즉 둘은 경쟁 관계가 아니라 서로 보완한다.

모든 revision이 RC일 필요는 없다.

하지만 ACT-001 요청의 의미가 실질적으로 변경되었다면 해당 revision은 RC에 연결되어야 한다.

---

# 14. 업무/결재 연결

RC가 기존 업무에 영향을 주면 해당 `W-ID`에 연결한다.

필요한 경우 work item에도:

- 관련 request
- 관련 request change

를 추적할 수 있게 한다.

RC가 이미 승인된 결정 범위를 바꾸려는 경우:

RC 생성만으로 기존 승인을 변경하지 않는다.

필요한 경우:

변경 요청
→ 검토
→ 새/수정된 D-ID
→ 공식 반영

순서를 따른다.

**RC 생성 ≠ 승인**

**RC 생성 ≠ 업무 완료**

**RC 생성 ≠ 공식 정책 확정**

---

# 15. 관리자 프로젝트 지침 반영

관리자 ChatGPT 프로젝트의 로컬 지침에서도 이 원칙을 알 수 있게 한다.

`chatgpt/admin/PROJECT_INSTRUCTIONS.md`

및 관리자 배포용 `ROLE.md` 또는 현재 역할 소스에서 적절한 위치에 다음 의미를 추가한다.

관리자 ACT-001의 기존 회사 요청이 의미 있게 변경되면:

- 기존 원문을 덮어쓰지 않는다.
- R-ID를 유지한다.
- RC-ID 변경이력을 남긴다.
- 변경 전/후를 기록한다.
- 변경 이유와 근거를 기록한다.
- 이유를 모르면 추측하지 않는다.
- 관련 W-ID/D-ID에 연결한다.

GitHub 조회 전에도 “관리자 요청 변경은 추적해야 한다”는 행동 원칙 정도는 프로젝트 소스가 알고 있어야 한다.

실제 저장 시에는 최신 GitHub workflow를 읽고 실행한다.

---

# 16. 대표님·부사수 프로젝트 경계

대표님과 부사수에게 관리자 전용 RC 의무를 추가하지 않는다.

공통 파일을 수정해야 한다면:

- 관리자 전용 규칙임을 명확히 조건화
- ACT-002 / ACT-003 권한 확대 금지
- 관리자 결재권 추가 금지
- 관리자 기록 열람 권한 추가 금지

세 역할 경계가 그대로 유지되는지 검증한다.

# 17. Workflow 반영

현재 `REQUEST_CAPTURE.md`를 중심으로 구현한다.

단순히 문서 한 줄만 추가하지 말고 실제 저장 절차에 연결한다.

다음을 정의한다.

1. 기존 request 조회
2. 현재 관리자 발언과 비교
3. 의미 있는 변경인지 판단
4. RC-ID 중복 여부 확인
5. RC 저장
6. request revision/update
7. request\_change\_refs 연결
8. 관련 index 갱신
9. 관련 W/D 연결 필요 여부 처리
10. 저장 후 파일 재조회
11. 실패/부분 실패 보고

현재 구조상 별도 workflow 파일이 실질적으로 도움이 되면 예:

`REQUEST_CHANGE_WORKFLOW.md`

를 추가할 수 있다.

하지만 파일 숫자를 늘리기 위한 형식적인 분리는 하지 않는다.

기존 `REQUEST_CAPTURE.md` 확장이 더 자연스러우면 그쪽에 통합한다.

실제 저장소 구조를 보고 결정한다.

# 18. COMMON\_IO / 실패 처리

현재 `COMMON_IO.md`의 저장 및 검증 원칙을 그대로 따른다.

특히 request와 RC/index 갱신 중 일부만 성공했을 경우:

- 전체 성공이라고 보고하지 않는다.
- 어떤 파일까지 저장됐는지 밝힌다.
- 복구 또는 재시도 필요 상태를 남긴다.

가능하면 하나의 논리적 변경으로 추적 가능하게 한다.

# 19. FILE\_MAP / Runtime / Registry 갱신

새 파일이나 새 읽기 경로가 생기면 필요한 범위에서:

- `FILE_MAP.json`

- 관련 README

# 20. 배포 소스 갱신

이번 변경은 관리자 ChatGPT 프로젝트 행동에 영향을 준다.

따라서 현재 저장소의 GOV 릴리스 방식에 따라 관리자용 배포 소스와 프로젝트 지침을 갱신한다.

현재 최신 GOV 번호를 확인하고 충돌 없이 다음 release ID를 발급한다.

현재 `GOV-20260906-03`이 여전히 최신이라면 일반적으로 다음은:

`GOV-20260906-04`

가 될 수 있지만, 반드시 실제 저장소를 확인하고 결정한다.

- 기존 아이디어/문제/결재 원문 변경 없음

### 기능 검증

Case A:

ACT-001 기존 요청의 의미 있는 변경

→ RC 생성되어야 함

Case B:

ACT-001 오탈자/표현만 수정

→ RC 생성하지 않아야 함

Case C:

ACT-001 변경 이유를 직접 말함

→ 실제 이유와 source 근거 저장

Case D:

변경 이유가 확인되지 않음

→ AI가 이유를 만들지 않고 unknown 처리

Case E:

RC 생성

→ 해당 요청이 자동 approved/done/official 상태가 되어서는 안 됨

Case F:

읽기 전용 명령

→ request/RC 자동 생성 금지

Case G:

대표님/부사수 request

→ 관리자 전용 RC 의무가 자동 적용되지 않음

Case H:

기존 ACT-001 request와 새 RC를 읽으면

→ 최초 요구 → 변경 전 → 변경 후 → 변경 이유 → 관련 W/D

를 재구성할 수 있어야 함.

# 22. 저장 안전성

작업 전:

- 최신 branch 확인
- remote 확인
- dirty work 확인
- unrelated work 보존

작업 중:

- 관련 파일만 수정
- secrets / credentials / 개인정보 저장 금지
- 기존 기록 삭제 금지
- unrelated formatting churn 금지

Git 사용 시:

- 변경 범위를 명확히 확인
- staged diff 확인
- 관련 파일만 stage
- 변경 근거와 검증을 남긴다.

현재 저장소 규칙에서 task branch/PR/merge 절차가 정의되어 있으면 그 절차를 따른다.

`main` 반영 또는 병합이 별도 승인 대상으로 정의되어 있다면 그 경계를 임의로 우회하지 말고, 반영 직전 상태까지 완료한 후 정확히 보고한다.
